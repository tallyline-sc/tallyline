# Diagnostics export foundation

> **Doc type:** Living reference — application and file contracts implemented; desktop composition pending. Last reviewed: 2026-11-03.

The #94 foundation prepares support evidence through the public Workflows application boundary before permitting a write. `DiagnosticInput` admits only four named sections: compiled version information, selected non-credential preferences, connection-test metadata and application-log tails. A raw input and the privacy context have redacted debug representations. No raw capture, arbitrary filename or `Game.log` section exists in this contract. Callers must collect only these permitted sources; this boundary does not authorise copying raw HTTP bodies or game logs into an application-log section.

`DiagnosticExportApplication::prepare` masks the supplied source snapshot and returns immutable entries named `build.txt`, `settings.txt`, `connection.txt` and `logs.txt`, in that order when present. The caller can list every included entry and inspect its exact masked text before saving. The public-attachment acknowledgement consumes that preview to produce `ConfirmedDiagnosticExport`; the sink receives only those frozen entries and cannot recollect different source data through this port. A failed sink write is returned without an automatic retry or a successful-export claim.

## Privacy and resource bounds

The privacy context contains the current secret key, app token and UEX/OS identity strings supplied by application composition. It is neither printed nor serialised. Rules and input share the same per-character lowercase-then-uppercase expansion, including sigma and sharp-S variants. Matching preserves original UTF-8 boundaries and covers every overlapping occurrence without removing neighbouring context. Prepared prefix tables keep matching linear per rule and fallback work bounded by the current matched prefix. An empty rule set returns before normalising the text or allocating search buffers. URL userinfo is removed while retaining the destination host. If removing userinfo would leave only a fragment of a known private value, the whole line is omitted; wholly removed values and disjoint masked values preserve useful context. Matching is applied again after removal, including private values formed by joining the remaining URL text. Lines containing e-mail addresses, image-payload markers or Discord data are omitted; long encoded runs and oversized lines are omitted as a defence against unlabelled payloads. This filter supplements source admission and the planned before-formatting logging policy; it does not make arbitrary request dumps a permitted source.

The fixed limits are 32 privacy values, 4,096 bytes per value and 16 KiB in total; empty/control-bearing values are refused. At most four distinct sections are admitted. Each input and masked output section is limited to 512 KiB. A line exceeding 4,096 bytes, or a run of at least 80 Base64-compatible bytes, is omitted as a whole. Invalid section/privacy budgets fail the request; line omissions are explicitly labelled. These limits bound the work and retained text of an explicit support action; they are not OCR performance measurements or user-adjustable thresholds.

## Application-log collection

`DiagnosticLogFiles` reads only `tallyline.log`, `tallyline.1.log` and `tallyline.2.log` below the resolved application-log directory. It never enumerates other files. An absent directory or absent permitted files yields no log section; relative paths, visible links, non-files, invalid UTF-8 and observed changes during a read are refused without exposing a path or source bytes.

Each file contributes at most a 64 KiB tail, with one extra byte read to establish its starting line boundary. A clipped first record and an unfinished final record are discarded completely. This prevents an incomplete private value at a byte-window boundary from escaping whole-value masking. Retained complete records are then passed through the same masked-preview boundary. An empty safe window is labelled without treating a fragment as a complete log record. These checks do not claim an atomic filesystem snapshot against an adversarial writer.

## Saved format

`DiagnosticFileExport` writes one JSON document with `format_version: 1` and a `files` array containing only the confirmed names/text. The encoded document is bounded to 16 MiB. The existing exclusive private-artifact writer requires an absolute destination, refuses existing files or links, synchronises the new file and uses owner-only mode 0600 on Unix; Windows inherits the explicitly selected directory's ACL. Errors contain no path or diagnostic content. A failed write may leave an incomplete new file, which is never reported as a completed export. No original file, setting, report or credential is changed.

## Verification and remaining work

Outside-in contracts exercise a DEBUG-style submit/VLM log, known credentials and identities in multiple cases, URL userinfo, e-mail/Discord fields and image payloads, along with ordinary context preservation, Unicode matching, overlapping values, negative budgets and accepted boundary values. They also preserve exactly maximum-sized masked output, useful redacted Debug summaries and each authority's host/context when several authenticated URLs occur together. Greek case variants, sharp-S and ligature expansion, self-overlapping values and an exhaustive small-pattern comparison cover the private-value boundary. Real temporary-file contracts verify the JSON contents, exclusive writes, closed failures, fixed-name log admission and complete-record tail handling. Unix permission/link contracts remain separate from the local Windows result. No real credential, game log or screenshot was used.
