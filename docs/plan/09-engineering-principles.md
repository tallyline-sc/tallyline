# Engineering Principles: Modularisation, Maintainability, Clean Code

> **Doc type:** Living spec — binding. Last reviewed: 2026-11-07.

This document makes "best practices" **verifiable**: every rule states *how* it is enforced. Where possible this happens automatically (compiler, the Cargo crate graph, Clippy, `cargo-deny`, `xtask`, CI), otherwise via the review checklist and the Definition of Done.

Rules without enforcement are wishful thinking. That is why there are deliberately few rules, and they are binding.

Amended 2026-10-12: the mechanisms were converted from Java 27, JavaFX and Gradle to Rust and egui ([ADR-0005](../adr/0005-rust-and-egui.md)). The rules themselves are unchanged unless a section says otherwise; "module" below means a Cargo workspace crate where the rule is about the context cut ([ADR-0002](../adr/0002-modules-by-bounded-context.md), amended by ADR-0005). Crate, package and binary names are fixed by O-122; the context names of 02 §2 are used here as working names. Every lint, tool and crate that this document names without a version is chosen and verified at source in M0 (§12).

## 1. Quality goals (descending priority)

1. **Correctness of the submitted data:** no silently wrong values sent to UEX.
2. **Maintainability:** SC patches change the terminal layout, UEX changes the API. Such changes should stay local to one crate.
3. **Testability:** domain logic testable without UI, network, database and game.
4. **Security and privacy:** secret key, balance.
5. **Portability:** Windows and Linux.
6. **Resource efficiency** alongside the running game.

## 2. Modularisation

| Rule | Enforcement |
|---|---|
| Ports & Adapters: the core crates (`shared-kernel`, the context crates, `workflows`) know no technology | Four layers, so that no single mechanism has to be perfect:<br/>• **Cargo edges:** `cargo xtask check` reads `cargo metadata` and allows a core crate to depend only on core crates along the context map and on a short, reviewed allowlist of pure crates (no I/O, no threads, no FFI; `tracing` as the logging facade belongs to it). The list lives in `xtask/src/architecture.rs` (CODEOWNERS).<br/>• **`cargo-deny` `bans`:** the technology crates (async runtime, HTTP client, SQLite binding, ONNX binding, UI toolkit, image codecs, serialisation formats of the adapters) are banned workspace-wide and allowed per crate through `wrappers`; so a core crate cannot even name their types.<br/>• **Clippy** `disallowed_types`, `disallowed_methods` and `disallowed_macros` in a `clippy.toml` of each core crate (kept identical by an `xtask` test): no `std::fs`, `std::path::Path`/`PathBuf`, `std::net`, `std::process`, `std::env`, `std::thread`, no `std::io::stdout`/`stderr`, no `std::time::SystemTime::now` and `Instant::now` (time only via the injected `Clock`), no loading of libraries, no `std::sync` mutexes, atomics and cells (§3, immutability). Images enter as `ImageRaster`, locations as `FolderLocation`.<br/>• **As a second check** the `xtask` rejects core dependencies outside the pure-crate allowlist. |
| Crates cut by bounded context ([ADR-0002](../adr/0002-modules-by-bounded-context.md)); dependency direction as in the context map in [02 §2](02-architecture.md), free of cycles | `cargo xtask check` reads `cargo metadata`, compares workspace edges with the context map, rejects cycles, unknown workspace crates and `submission → reporting`; fixture tests cover each rejection. Cargo also rejects dependency cycles before metadata can be produced. Module cycles **within** a crate remain caught by an `xtask` test over the `use crate::…` graph of the top-level feature modules (parsed with a Rust parser crate chosen in M0) |
| Every crate has a narrow public API | The `lib.rs` of a context crate declares `pub mod api` (with `pub mod model`) for the types that ports and other contexts must name; the implementation lives in `pub(crate)` modules. Rust's privacy rules make another crate's internals unreachable; an `xtask` test checks that `lib.rs` has no other `pub` item |
| Adapters do not depend on each other; they are leaves (only `app` and the second composition root `tools/ocr-eval` may depend on adapters) | `cargo xtask check` rejects adapter-to-adapter and otherwise unmapped workspace edges from `cargo metadata`; `ui` depends only on the context crates' `api` and `workflows` (02 §2); allowed edges are listed once in the `xtask` |
| `shared-kernel` contains only value objects, IDs, `Outcome`, event base, the `LogContext` span fields (§4) and marker types used by at least two contexts | `xtask` snapshot test of its public item names (no aggregates, services or ports); CODEOWNERS review for every change |
| Cross-context processes only in `workflows`; context crates never call each other's application services backwards against the context map | Cargo edges (a missing dependency does not compile) plus the `xtask` edge test |
| No passing of technology types across crate boundaries (DTOs, database rows, `ort` sessions, `egui` types) | The technology crates are banned in the core (row 1), so their types cannot appear in a port. Port signatures use only the exported types (`api`/`api::model`) of their own crate, of `shared-kernel`, or of upstream context crates along the context map in [02 §2](02-architecture.md) (published language, e.g. `GameEnvironment`, `GameVersion`, `Finding`), plus pure `core`/`alloc`/`std` types; adapters map at the boundary (review) |
| Package-by-feature within a crate (e.g. `recognition::locate`, `recognition::parse`, `recognition::stitch`) instead of package-by-layer | Review checklist |
| `app` contains only wiring and startup | `xtask` test: the `app` crate contains only `main.rs`, `*_wiring` modules, the context-carrying spawn helper (§4) and the bootstrap loader (storage locations per 02 §8, portable marker; user settings go through the `*SettingsStore` ports in `adapter-files`, and the wiring passes setting values to adapters as closures backed by the stores, 02 §2); line budget as a review hint |
| No service locator, no static singletons, no global mutable state | rustc `static_mut_refs` at deny; Clippy `disallowed_types` (`OnceLock`, `LazyLock`, `OnceCell` and the interior-mutable `std::sync` types) and `disallowed_macros` (`thread_local!`) in every crate; `static` only for immutable constants; `tracing::subscriber::set_global_default` is `disallowed_methods` everywhere except `app` |
| Memory safety by default | `#![forbid(unsafe_code)]` in every crate except the platform adapter (D1 of [ADR-0005](../adr/0005-rust-and-egui.md)); an `xtask` test checks the attribute in every `lib.rs` and `main.rs`; the platform adapter uses `#![deny(unsafe_code)]` and every site is registered in §3a |

## 3. Clean Code

Credential dependency exclusion guard, 2026-11-01: `cargo xtask native-scope` and `check` reject any reachable `memoffset` or `uds_windows` version on either supported target, including renamed transitive edges. These identities remain outside the approved credential scope; a lockfile-only disposition is not activation permission. Corrected 2026-11-02: the credential dependency foundation and qualified S-6 records are adopted below; these two identities remain lockfile-only and prohibited on supported targets.

| **Uniform formatting** | `cargo fmt --check` (rustfmt, default style, a `rustfmt.toml` only if M0 shows a need) in the check suite; formatting is never discussed by hand |
| **Warnings are errors:** no lint finding is left standing | `-D warnings` for rustc and Clippy in CI (`cargo clippy --workspace --all-targets --locked -- -D warnings`); lints are configured once in the workspace `[lints]` table and never relaxed per crate without a §3a row |

## 3a. Suppression register

A suppression (`#[allow]` or `#[expect]` with its `reason`, a lint set to `allow` in a `[lints]` table, a `deny.toml` `skip` or `ignore` entry, a `cargo-vet` exemption, an `osv-scanner.toml` exception) is allowed only where the rule is genuinely wrong at that site. For `deny.toml`, `cargo xtask check` enforces this (10 S-6): a `skip`, `skip-tree`, `ignore`, licence `exceptions` or `clarify` entry fails the check unless its row here names `deny.toml` and the entry (the crate spec or advisory ID) in backticks and ends with a revisit date, and unless the entry carries a non-empty `reason` where its key has the field. It carries a one-sentence `reason` where the mechanism has the field (never a comment), and it gets a row here together with the reasoning in the commit message and the pull request. Advisory and OSV exceptions ([10](10-supply-chain-security.md) S-19) are rows whose "Revisit when" is their expiry date. A row is removed together with its suppression.

The `unsafe` code of the platform adapter is registered here too. Corrected 2026-11-01 (issue #104): the planned edition-2024 `std::env::set_var` site is unnecessary. The application safely relaunches its own absolute executable with the mitigation in the child environment before instance election or threads, and refuses a failed first bootstrap (02 §8 implementation note). The accepted ADR-0008 mitigation effect and Windows ETW acceptance remain unchanged. Further platform FFI of the adapter (D1) gets its own row.

## 3b. Native-code exception register

Corrected 2026-11-03: the native-scope pre-build step enforces the adopted exact property-testing archive/source/feature/target record and sole recognition dev introduction. The owner approved only getrandom 0.4.3's std,sys_rng test-feature extension; its source/backend/build-script identities remain unchanged. Separate test and normal/build trees preserve host dependencies through conservative metadata. This adds no C/C++/assembler exception. See [the guard's scope and limits](../../xtask/README.md#property-testing-profile-preparation); matching-host runtime/release evidence remains separate.

Our own code is Rust only. A dependency must be pure Rust when a mature pure-Rust crate exists; native code (C, C++, assembler) in a dependency is allowed only as a registered exception (D1 and D2 of [ADR-0005](../adr/0005-rust-and-egui.md)). A new dependency that brings native code needs its row here in the same pull request and the project owner's approval; the row names the reason, the licence (checked against the licence policy in [CLAUDE.md](../../CLAUDE.md) "Stack rules") and the condition under which the exception is revisited. An `xtask` test over `cargo metadata` fails if a package with a `links` key or a build dependency that compiles native code (`cc`, `cmake` and similar) appears in the resolved graph without a row for the crate that pulls it in. Native parts also enter `NOTICE` and the hand-kept list of the licence gate ([10](10-supply-chain-security.md) S-34), and their build scripts the review list of S-12.

Corrected 2026-11-01 (narrow enforcement): the `native scope` step of `cargo xtask check` enforces the explicit package and feature restrictions: `wayland-backend` 0.3.17 feature `log` stays disabled, and `android-activity` 0.6.1 and `objc-sys` 0.3.5 remain absent from the supported Windows and Linux target graphs. It checks active resolved features and package-ID reachability from all workspace roots in full locked, target-filtered metadata; malformed reachable graph data fails. Later native activation needs new owner approval. The same guard excludes every version of `android-properties`, `core-graphics`, `dispatch` and `send_wrapper` from both supported graphs. The unresolved optional Future/Stream Pin projection and wrong-thread Drop/leak concern in `send_wrapper` grants no source-soundness audit or publisher trust; activation needs a focussed source review and owner approval. The S-6 Apple proxy exclusions also reject every reachable version of `system-configuration` and `system-configuration-sys`. Failed native-scope and S-12 checks stop the aggregate check before workspace build/test work. The public metadata fixtures cover negative activation/leakage, renamed transitive dependencies from alternative workspace roots, future versions and correctly excluded packages; see [`xtask/README.md`](../../xtask/README.md#approved-native-scope-restrictions). The separate S-12 reviewed list and literal assembly inventory are now enforced; semantic detection of arbitrary native code remains limited: a `links` marker alone does not prove native code (`rayon-core` and `wasm-bindgen-shared` have pure-Rust coordination markers), and this step does not audit arbitrary build scripts. This status note does not waive the preceding requirements or complete M0.

## 4. Error handling, logging, observability

Implementation checkpoint 2026-11-02 (#94): [the diagnostics foundation](../diagnostics-export.md) provides bounded masked previews and exclusive private JSON writes, with fixed-name complete-record application-log tails. The actual tracing writer, connection-test worker and desktop composition remain pending; this checkpoint does not fulfil the complete logging/export acceptance criteria below.

- **Error categories:**
  - domain (`Finding`, UEX status codes) → explained to the user
  - technically expected (network down, file locked) → retry or notice
  - programming errors → panic, logged at ERROR by the panic hook, diagnostics export
- **User texts** only via keys in the message catalogues (the format is chosen in M0), with English texts; error codes are mapped to keys centrally (one table, covered by tests: every known UEX code has a text).
- **Logging:** `tracing` only. Dependencies that log through the `log` crate or their own callback (ONNX Runtime) are bridged into `tracing` in `app` (bridge crate chosen in M0). No `println!`, `eprintln!`, `dbg!` or `std::io::stdout`/`stderr` in library and `app` code (Clippy `print_stdout`, `print_stderr`, `dbg_macro` at deny, plus `disallowed_methods`), and no second logging facade; the CLI tools under `tools/` may write to the console.
  - **Context** via `tracing` spans (`captureId`, `reportId`). The core opens a span that carries the `LogContext` fields (`Option<CaptureId>`, `Option<ReportId>`; type in `shared-kernel`). A span does not follow a task onto another thread or executor by itself, so `app` provides **one** helper through which every unit of work is started (async tasks on the tokio runtime, jobs on the bounded OCR, image and SQLite pools, the UI executor): at submit time it captures `Span::current()`; a future is wrapped with `Instrument::instrument`, a pool job runs inside `span.in_scope(…)`. Without a context the task runs in an empty span. One parameterised test (bounded pool, tokio task, direct executor) proves that the context is visible inside the task and gone afterwards. The masking layer (below) lives in the same subscriber set-up in `app`.
  - **Content:** secrets, image data (the `/data_submit` `screenshot` field, Ollama `images`, raster bytes) and complete request or response bodies are never logged, at any level. At DEBUG, payloads are summarised (row count, byte sizes, SHA-256). A `tracing` masking layer in `app` redacts the secret key and token fields; `Debug` implementations of secret-bearing and image-bearing types print only a summary. `GameProcessMonitor` logs only matched/not matched plus the matched executable path, never other processes' command lines. Tests prove that the masking layer takes effect and that a DEBUG-level submit and VLM call log no Base64 image data.

## 5. Concurrency

- Shared state is immutable. Mutable state has **exactly one owner** (e.g. the queue service) and is changed only via its API or messages on a channel; views and background work talk to it through channels, never through shared locks (ADR-0005 D3).
- Runtime and pools follow ADR-0005 D4: I/O runs as tokio tasks (`reqwest`, rustls); CPU-heavy work (OCR with the typed `OcrRuntimeSettings`, never the ONNX defaults; image decoding and encoding; content hashing) runs on **bounded** dedicated thread pools, never on the async runtime and never on the UI thread; the CPU ceiling is pool size × intra-op threads (02 §7, R-NF-3). SQLite, ONNX Runtime and image-codec calls block, so they only run on those pools. These workers run below normal OS priority (R-NF-3, 02 §7).
- Pools and runtimes are injected and shut down in an orderly way (an owner type in `app` drops them in a defined order; tests prove that shutdown joins). There are no self-created threads or tasks in domain code. Only `app` (and the second composition root `tools/ocr-eval` for its own runs, and the M0 API spike binary `tallyline-uex-spike` of `adapter-uex`, which builds one current-thread runtime in its `main` and writes to the console like a tool) creates runtimes, pools and threads: Clippy `disallowed_methods` forbids `std::thread::spawn`, `std::thread::Builder::spawn`, `std::thread::scope`, `tokio::spawn`, `tokio::task::spawn_blocking` and `tokio::runtime::Builder` in every other crate. Adapters receive injected handles (folder-watcher loop, game monitor) or run their `reqwest` client on the runtime that `app` owns (`adapter-uex`, `adapter-vlm`; amended 2026-10-14: `adapter-uex` builds its client itself from its settings, so that the TLS configuration of ADR-0006 stays in one place, and the client runs on the caller's runtime); all work starts through the context-carrying helper of §4.
- Cancellation is a regular path: AI run, import and submission are cancellable (a cancellation token passed to the work; the type is chosen in M0), and this is tested. A user cancel is refused once a submission job is `sending`; a shutdown, crash or kill after that leads to an unknown outcome, never to a re-send (R-SUB-9).
- Time always comes via the injected `Clock` port: this makes cooldown, hysteresis and grouping deterministically testable. The core has no access to the runtime's timers (`tokio` is banned there, §2).

## 6. Persistence

- `adapter-storage` owns the connection. Every domain table belongs to exactly one repository.
- **No SQL outside the repositories** (`cargo-deny` `wrappers`: `rusqlite` is allowed only for `adapter-storage`, so no other crate can name a connection or a row).
- Schema migrations are versioned, forward-only and each has a test (empty DB → current version; previous version with test data → current version).
- The configuration file has one schema version, one migration and one writer: all `*SettingsStore` implementations share the `ConfigFile` component in `adapter-files` (02 §2; F17).

## 7. UI (egui)

- **Views are functions of an owned state value** (ADR-0005 D3): a view takes `&State`, draws, and returns messages; it contains no logic and no thresholds. Commands to the rest of the app go through channels. The state types and their `update` functions (message → new state + commands) live in modules without any `egui` import, so they are unit-testable without a window.
- Formatting (numbers, Δ %, "3 days ago") lives in **one** place (formatter module) and is localised.
- The display of deviation and confidence is derived from `Field` (assessment, confirmation, origin) by a mapping to the style classes of 02 §7 and the Tallyline tokens; the state contains no thresholds. Colours exist only in the theme module (Tallyline tokens, [ADR-0004](../adr/0004-design-system.md) as amended by ADR-0005): an `xtask` check rejects colour literals (`Color32::from_*` and similar) outside it.
- **Dialogs only from user actions** (R-UI-16): dialogs and windows are opened only through one `ui` module, the `DialogPresenter`. An `xtask` check over the `ui` sources rejects, outside that module, constructing a dialog or an extra viewport and any of the viewport commands that focus, raise, minimise, maximise, restore, show or hide a window, request user attention or set a window level (including always-on-top); moving the focus owner inside the current window (`Memory::request_focus`) is allowed for keyboard navigation (R-UI-17). Message-handler tests feed every background event type in and assert that no dialog request comes out, only state or notice changes. One UI test checks that a background event while the window is unfocused or minimised creates no new viewport and changes neither the focus nor the minimised state.
- **Rendering load next to the game** (R-NF-3): the UI repaints only on input and on state change, not continuously, and shows no indeterminate progress. The `xtask` check over `ui` rejects `Context::request_repaint` outside the single wake-up helper (called when a channel message arrives; timers use `request_repaint_after` with a typed interval from the settings), the `Spinner` widget, indeterminate or animated progress bars and the `animate_*` helpers of the egui context; message-handler tests assert that progress values are never negative. A frame-count test with the UI test harness (O-114) asserts that an idle window produces no repaint.

## 11. Process: Definition of Done and review checklist

**Definition of Done** for every change (the aggregate command that runs the whole suite is fixed in M0 and named in [CLAUDE.md](../../CLAUDE.md); build and test only through Cargo and `xtask`, never through an IDE test runner):

- [ ] The check suite is green on Windows and Linux (CI matrix): `cargo fmt --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `cargo test --workspace --locked`, `cargo doc --workspace --no-deps --locked` with rustdoc warnings denied, `cargo deny check`, the `xtask` checks (architecture, comments, English, headers), and the `cargo-llvm-cov` gate
- [ ] Developed via TDD in the core: test first (red), then implementation (green), then refactoring; bugfix with a reproducing test
- [ ] Domain terms match the Ubiquitous Language (11 §A1); aggregate invariants are covered by tests
- [ ] No new `xtask` architecture, Clippy or `cargo-deny` finding; a suppression only with its row in the suppression register (§3a), its one-sentence `reason` attribute and the reasoning in the commit message and the pull request, never in a code comment
- [ ] No comments besides rustdoc, also none in configuration files (§3)
- [ ] No new `unsafe` and no new native code; where unavoidable, a row in §3a or §3b with the project owner's approval
- [ ] UI texts in English, via the message catalogues (no hard-coded strings)
- [ ] Affected plan or ADR documents updated in the same commit; a user-visible change also updates `README.md`, the user guide (`docs/user/`) and `CHANGELOG.md`
- [ ] No secrets, private screenshots or large binary files in the diff
- [ ] For changed dependencies: `Cargo.lock` and the `cargo-vet` files (and the vendor hash list, if kept) updated in the same PR as a separate commit (10 S-5); new crates and their publishers checked and documented in the PR; a new crate audited or imported, never added to the bootstrap exemptions of `cargo-vet` (10 S-6, the procedure is in `supply-chain/README.md`); a Dependabot pull request gets its vendor hash and audit follow-up commits (10 S-8); a new build script or procedural macro on the S-12 list; a moved action pin or CI tool pin updates its row in `docs/dependency-pins.md`
- [ ] A shipped component or bundled asset: its licence is allowed by the licence policy (§9); `NOTICE` entry, `REUSE.toml` annotation, licence text under `LICENSES/` and SHA-256 for bundled files; licence gate and `reuse lint` green
- [ ] The Star Citizen Fan Kit unit is unchanged (logo file and both notices byte for byte, rendered together, pinning tests unchanged), unless the project owner approved the change (R-UI-19)
- [ ] A new network destination, a new kind of data sent or a new local store: the data-flow inventory (02 §9) is updated, with the project owner's approval
- [ ] A change to the UI, the crate graph, the bundled libraries, resources or packaging is verified by launching the app (and, for packaging, the installed package), not only by tests
- [ ] Every commit has a Conventional Commits message and a DCO sign-off made with `git commit -s` that matches its author; the author is on the CLA roster (`docs/cla-signatures.md`); AI involvement is named in a `Co-Authored-By:` trailer

**Review checklist** (PR template `.github/PULL_REQUEST_TEMPLATE.md`):

- Is the code in the right crate and module? Is a new crate edge needed – and allowed?
- Is the domain logic free of technology?
- Are there magic numbers, boolean parameters, sentinel values or swallowed errors?
- Do names conform to the glossary?
- Are error cases and cancellation handled and tested?
- Is a new `unsafe` block, native dependency, build script or procedural macro justified and registered?
- Is the change as small as possible (one thing per PR)?
