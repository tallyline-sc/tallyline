# Release and hotfix process

> **Doc type:** Living spec — binding; followed from release 0.1 on. Last reviewed: 2026-11-07.

Implements R-NF-11 and the release-related parts of [10-supply-chain-security.md](plan/10-supply-chain-security.md). This is a plan; it is followed from release 0.1 on and refined with experience. Amended 2026-10-12: the implementation language is Rust ([ADR-0005](adr/0005-rust-and-egui.md)), so the Java, Gradle, jlink and jpackage steps became their Rust equivalents (`cargo xtask`, `cargo-packager`, the Rust toolchain pin); commands and tool versions that ADR-0005 does not name are chosen and verified in M0.

## Versioning

- SemVer: `MAJOR.MINOR.PATCH`.
  - PATCH: fixes and recognition-profile updates.
  - MINOR: features.
  - MAJOR: a change to persisted data after which a downgrade loses data or needs the user to act. Every format change still ships a tested forward migration (09 §6, §10).
- The app version is shown in the UI, written to the logs and sent in the User-Agent and the `X-Client-Version` header (R-API-7, O-86).
- `CHANGELOG.md` follows "Keep a Changelog" with an `[Unreleased]` section. Every user-visible change adds its entry in the same commit as the change: one to three sentences on what changed and why it matters to the user, plus the requirement ID ([CLAUDE.md](../CLAUDE.md)).
- The version comes only from the signed `v<MAJOR>.<MINOR>.<PATCH>` tag: CI passes it to the build, which writes it into the build information read by the UI, the logs and the User-Agent (the mechanism is chosen in M0); nobody edits a version by hand, and local builds carry a fixed development version.

## Release checklist

1. `main` is green on Windows and Linux: `cargo xtask check` (format check, Clippy with `-D warnings`, rustdoc lints, all tests, the architecture rules over `cargo metadata`, `cargo-deny`, coverage gate); the full `cargo-mutants` run on the release commit meets the mutation-score gate (11 §B3); the OSV scan and `cargo-audit` (S-19) on the release commit show no blocking finding (runtime dependencies, CVSS ≥ 7.0 or unscored), apart from documented exceptions that have not expired; the native-code exception register (09 §3b) has no entry past its revisit date.
2. Corpus evaluation (R-QA-3): no regression in any gated class or new silently wrong field; list every required non-gated class as not verified with capture guidance. Evaluate private-only classes locally with `TALLYLINE_CORPUS_DIR`. A changed recommended local recognition profile needs its bake-off report and release-versioned exact engine/model/projector/dictionary/prompt/preprocessing hashes, installation size, hardware conditions and metrics (R-VLM-11, S-27). Verify the initial selected profile works without a separate programme or later installation (ADR-0012); the outstanding ADR-0009 OCR prerequisite must be resolved before claiming that delivery goal.
3. Live smoke test against UEX with `is_production=0`, the release candidate's built-in app token and the tester's own key (manual, opt-in): onboarding check, one manual report, one OCR report with several captures (one submission per capture, O-137). Decided 2026-10-09 (O-89): the earlier "one withdrawal" step is removed until UEX confirms that `data_remove` works on `is_production=0` submissions ([06](plan/06-uex-api.md) open point 29), because a withdrawal must never touch production data. Settled 2026-10-25: UEX never stores dry runs, so the step stays removed.
4. Database migrations tested: an empty DB and the DB of the previous release (with test data) migrate to the new version; the previous release refuses the new schema (R-NF-11); the pre-migration backup of a DB with an un-checkpointed WAL passes `PRAGMA integrity_check`, and restoring it in the previous release sends Released and Queued reports back to Draft and marks OutcomeUnknown ones (see 'After a restore').
5. Check that `CHANGELOG.md`, `README.md` and the user guide (`docs/user/`) are complete. They are updated with every user-visible change in the same commit; this step only checks them.
6. Create a signed tag on protected `main`. The release workflow then runs secret-free build jobs (prebuilt binaries and SBOM), separate protected packaging jobs that add the token data file without running project build code, and a separate publish job without Cargo that computes SHA256SUMS, attests and publishes (S-14 to S-18). The release notes record the Rust toolchain version (`rustc -vV` of the build), the ONNX Runtime library version and hash, and the installer tool versions (`cargo-packager`, WiX; S-11). The release also publishes the plain Windows app image as a ZIP next to the MSI and attaches the source archives of R-DOC-4 (see 'Licence compliance'); the release notes link the tag, which is the Corresponding Source.
7. Verify the published artifacts:
   - `gh attestation verify` on one artifact per OS;
   - install or unpack **every** published artifact (MSI, ZIP, `.deb`, `tar.gz`) on a clean Windows and a clean Linux machine (or VM) and start the app; on Linux start it once in an X11 session and once in a native Wayland session (R-NF-1);
   - from 1.0 on, the accessibility walkthrough of R-UI-17: keyboard-only use of the main flows, contrast in every theme including the high-contrast theme, colour never the only signal, 200 % text size at the minimum window size, and scale factors 100–250 % including a monitor pair with different scale factors. Screen-reader use (Narrator, NVDA) is a Could (R-UI-17a) and not part of this walkthrough.
   - licence duties (R-DOC-3, R-DOC-4, R-UI-18, R-UI-19): every artefact contains `LICENSE`, `NOTICE` and the notices directory; the `.deb` installs the DEP-5 `copyright` file; the MSI adds no licence terms; the About dialog shows the legal notices, the open-source licences and the source link of this version; the Fan Kit unit appears in the About dialog and on the onboarding start screen; the source archives are attached and match their pinned SHA-256 values.

## Licence compliance

The release duties that follow from the project licence (GPL-3.0-or-later, [ADR-0003](adr/0003-licence-and-contributions.md)) and from the licences of the bundled components. `NOTICE` lists every component.

- **Notices.** Every installer and archive ships `LICENSE`, `NOTICE` and the notices directory (R-DOC-3), assembled from the shipped artefacts, not from upstream repositories (the two can differ). The About dialog shows the Appropriate Legal Notices, the notices of the native parts and the credits of `NOTICE` §6 (R-UI-18). Statically linked crates leave no licence files next to the binary, so `cargo xtask notices` exports the licence and notice files of the shipped crates and of the reviewed list (`supply-chain/notices.toml`) into the notices directory `legal/` and fails when an entry lacks its files; the packaging step copies that directory into every artefact.
- **Source archives.** Every GitHub release links the tagged source and attaches the complete source of every shipped component under GPL-2.0, LGPL, MPL-2.0 or MS-RL (R-DOC-4): Eigen at the commit ONNX Runtime pins, any LGPL or MPL-2.0 crate among the vendored sources (the vendor tree is regenerated from locked sources and verified against committed hashes; corrected 2026-11-01, O-120), and the source of the WiX files in the MSI. A read-only build job fetches what is not in the tagged source from pinned URLs and checks it against committed SHA-256 values; the publish job attaches it. Permissive components are linked from `NOTICE` by crate version. Whether ONNX Runtime's other native dependencies are archived as well is open.
- **Windows packages.** Next to the MSI the release publishes the plain app as a ZIP, so the GPL work is also available outside the MSI, which embeds MS-RL files of WiX; the MS-RL text and the WiX source go with every MSI. The MSI adds no licence terms and shows no licence dialog (GPL-3.0 §9 requires no acceptance).
- **WiX version and EULA.** The installer is built by `cargo-packager` with a WiX Toolset installed beforehand and pinned by SHA-256 in [`dependency-pins.md`](dependency-pins.md); the packager downloads nothing (ADR-0005 D7, O-116). The pinned version is WiX 3.11.2, which has no Open Source Maintenance Fee EULA. From WiX v6 on the official binaries come with that EULA; such a version is used only after the project owner has accepted the EULA explicitly, recorded here:

  | WiX version | OSMF EULA | Accepted by | Date |
  |---|---|---|---|
  | 3.11.2 | none (WiX 3 has no maintenance-fee EULA, ADR-0005 D7) | – | – |

- **`.deb`.** The default `copyright` file of the packager is replaced with a DEP-5 file that lists the bundled components and their licences; the mechanism, and the plain ZIP and `tar.gz` built by `xtask`, are verified in the M1 spike (O-116).
- **Before the first release only:** a legal review of the Windows app's dependency on the Microsoft C/C++ runtime DLLs that the ONNX Runtime library needs (our own binary can link the C runtime statically). The packages do not ship them; the Visual C++ Redistributable is a prerequisite (ADR-0009, R-NF-13). Until then the project relies on the GPL-3.0 System Library definition. Whether a narrow GPL-3.0 §7 additional permission is added is decided before the first external contribution (O-12).
- **Star Citizen Fan Kit.** `NOTICE` §4 records the checked kit version (`Fankit_2025_11_19`). The Fankit Agreement lets Cloud Imperium change its documents (clause 11, as recorded in basetool); when a newer kit is published, the project owner re-checks the unit (R-UI-19) against it before the next release.

## Security release

Users get fixes for the linked crates and native libraries only through our releases (10, ADR-0005). There is no quarterly runtime duty any more (the quarterly JDK security releases of the earlier Java plan are gone): the standard library is linked into the binary at build time, and only a security fix in the compiler or the standard library triggers a rebuild; dependency security releases stay.

1. **Triggers:**
   - a security fix in the Rust compiler, the standard library or the toolchain's bundled components that affects the shipped binary: rebuild with the fixed stable toolchain (the pin is raised in its own pull request, ADR-0005 D10; the scheduled pin check flags a pin that has fallen behind);
   - a blocking OSV or `cargo-audit` finding (S-19) against the latest release tag, or an advisory for a linked crate or a bundled native component (ONNX Runtime, SQLite, the TLS provider `aws-lc-rs`, `rustls`);
   - a confirmed report via `.github/SECURITY.md` (S-31).
2. **Procedure:** a PATCH release from `main` with the full release checklist, including the corpus evaluation (a toolchain, image-crate or ONNX Runtime update can change image decoding or recognition). Target: published within 7 days of the advisory or of the confirmed report (start value). The CHANGELOG and the release notes get a 'Security' entry; a confirmed vulnerability in our own code also gets a GitHub Security Advisory.

## Upgrade and downgrade

- **Backup:** before every migration the app, holding the single-instance lock (R-NF-10), opens the DB (this recovers a hot journal or WAL) and writes the backup through SQLite (`VACUUM INTO 'backup/<timestamp>-v<old>.db'` or the online backup API), never as a file copy. It checks the backup with `PRAGMA integrity_check` and aborts the migration if that fails, then writes a marker row (`backup_meta`: taken at, from version) into the backup. Every build from 0.1 on writes this marker. The config file is saved next to it under the same timestamp. Working copies are not backed up; a missing one is shown as 'image no longer available'. The last 3 backups are kept. An `adapter-storage` test takes a backup from a DB with an un-checkpointed WAL.
Implementation status 2026-11-01: `SqliteReferenceCache::backup_into` is the SQLite primitive for a pending backup set. It reserves a new destination, uses bound `VACUUM INTO`, checks integrity before and after writing `backup_meta`, closes the backup in DELETE journal mode and synchronises the file. The marker records decimal Unix milliseconds, `from_version` and nullable `config_schema`; `backup_metadata` reads it without clearing it and rejects multiple competing marker rows. Real-file contracts cover un-checkpointed committed WAL data, unchanged source records, no replacement of an existing destination and precise/absent marker fields. App coordination of this database primitive with the configuration hook and schema-one/two to schema-three forward migration is implemented; the generic completed-set retention and confirmed-no-database bootstrap are already implemented by `BackupSetStore`; this primitive alone does not claim the restore UI or Report/job transitions below are complete.
Corrected 2026-11-02: the application database now uses schema 4 for value-bound manual status decisions. Existing schemas 1, 2 and 3 require the same verified coordinated backup before forward migration; schema-three values and Report versions are preserved with no invented approval. Older schema-three builds refuse this newer database. Restore UI and Report/job transitions remain separately open.
- **Downgrade:** an older build that finds a newer schema version refuses to start with a clear message and never writes to the newer database. It offers **Restore backup** for the most recent compatible backup. The dialog shows the backup date and what is lost since then (history and withdrawal IDs, cooldowns, queue, processed-file register). The newer DB file is kept under a new name, never overwritten. Every build from 0.1 on has this action.
- **After a restore:** a build that opens a DB carrying a `backup_meta` marker treats it as restored, also after a manual file copy. Released reports go back to Draft by `cancel`, and queued jobs (including waiting, held or paused ones) are returned as after any restart (`SubmissionReturned`, R-SUB-2). Both get the finding `PossiblyAlreadyReceived` ('may have been sent by a newer version after <taken at>') and need explicit confirmation before release. `OutcomeUnknown` reports keep their state (there is no transition to Draft, 11 §A3), get the same finding and are resolved via `data_info` or by the user (R-SUB-9). The import and catch-up scans import files modified after <taken at> only with the finding 'possibly already submitted'. Then the marker is cleared. The hard observation-age limit (R-VAL-6) bounds the remaining risk.
- **Config file:** carries a schema version and has its own migration, with the same rules; it is backed up together with the DB.

## Star Citizen patch day (hotfix process)

1. **Detection.** The `UnvalidatedGameVersion` cap (R-OCR-19) protects UEX once the app has observed the new UEX game version (R-CAP-3b): from then on, recognised values of the new version are not sendable without confirmation. Before UEX publishes the new version, or if a patch keeps the version string, only the deviation checks (R-UI-10) apply (A17). Note when UEX published the new version, to verify that assumption.
2. **Capture.** On the new version, capture fresh screenshots for at least one blue and one orange terminal, buy and sell, and add them to the corpus (public after redaction, `corpus/README.md`). If the patch notes mention graphics options, HDR, the renderer, upscaling or screenshots, also capture one paired HDR on/off set with the SC screenshot key (if an HDR display is available; otherwise note the unchecked HDR behaviour in the changelog), and re-check every in-game setting name quoted in the user guide and the in-app hints (R-DOC-1, R-OCR-17, R-OCR-18). Outdated tips are corrected in the same PATCH release. Transcribe each new capture into `expected.json` with `conditions.gameVersion` set and have the transcription independently verified (`verified: true`) before step 3; unverified captures never validate a version (R-OCR-19).
3. **Measure.** Run the corpus evaluation (the eval disables the `UnvalidatedGameVersion` cap, 07 §4):
   - If no existing class regresses, add the new game version to each layout profile whose verified new-version captures meet the R-OCR-19 criteria (no silently wrong field, accuracy not below the profile's frozen baseline), and make a PATCH release. Profiles whose theme was not captured and verified on the new version keep the cap.
   - If something regresses, fix the layout profile or recognition rule test-first (11 §B1), then make a PATCH release.
4. **Target.** A validated profile within a few days of a patch. Until then the cap stays in place; manual confirmation still works.

## UEX API change

1. Contract tests with recorded responses fail, or users report errors (issue template with diagnostics bundle).
2. Verify the change against the live API with `is_production=0`; update `docs/plan/06-uex-api.md`.
3. Fix test-first and make a PATCH release.
4. If the faulty version sent bad data, coordinate with UEX: User-Agent and `X-Client-Version` identification (R-API-7), withdrawal via `data_remove` per row if needed (only rows not yet consolidated, R-SUB-4).
5. An HTML (non-JSON) HTTP 404 on a write holds the whole queue as "API changed" (R-SUB-11) until a PATCH release adapts the client or the user retries.
6. If the Tallyline app token is misused, @greluc writes to UEX, which sees the app's traffic and can disable the token on its side. Replacing the token means deleting and re-creating the app in "My Apps", which stops the old token at once for every installed release ([06](plan/06-uex-api.md) "Basics"); store the replacement only in the protected `release` environment and issue a PATCH release whose packaging jobs add it to the artefacts (O-139, [ADR-0010](adr/0010-release-token-delivery.md)). Installed releases need that update or the existing user-token override; until then `access_denied` pauses the queue with the invalid-token state (R-SUB-11). Each external write needs its own approval under the external-write rule.

## Release update notice

Verified 2026-11-01 against [GitHub's latest-release API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release): `GET /repos/tallyline-sc/tallyline/releases/latest` returns the latest published full release, excluding drafts and prereleases. GitHub documents selection by `created_at` (the release commit date), not publication time; the client uses this endpoint's selection and does not infer eligibility from the release list. It requires `tag_name`, `draft` and `prerelease` of the documented types, and independently rejects a draft, prerelease or tag outside this project's exact `vMAJOR.MINOR.PATCH` format. A missing eligible release (404) means no available update; other failures remain passive unavailable state. Numeric version order decides whether the release is newer, so a latest endpoint returning an older version never prompts a downgrade.

The notice constructs only `https://github.com/tallyline-sc/tallyline/releases/tag/<validated tag>` and opens it only on a direct user click. Assets, download URLs, response HTML links and bodies are discarded; the app downloads or launches no update code. The last validated available version and explicit dismissal persist across restarts; cached tags are validated again on load, and an installed version that is at least as new suppresses its old notice. Unavailable checks do not discard a known update. Checks are default off and limited to one attempted request per 24 hours across restarts, with the attempt committed before I/O. See [desktop guide](user/desktop.md#release-updates) and architecture N4. The installed version is an immutable composition input; source builds use their fixed development `CARGO_PKG_VERSION`. Issue #98 supplies the independently verified signed-tag release identity; no arbitrary environment override asserts a release here.

### Config-only bootstrap backups

Corrected 2026-11-01: before the first database exists, config migration still makes an exact-byte config backup. `adapter-files::BackupSetStore` confirms absence of the reserved `data/tallyline.db` path; an existing or unreadable database path refuses this coordinator. Once a database exists, the composition root supplies the SQLite-owning backup callback; it never falls back to copying the database or backing up only config.

Completed sets use `data/backup/<taken_at_ms>-v<previous_config_schema|none>/manifest.json`, with optional `settings.json` and optional SQLite-created `tallyline.db` siblings. The manifest has `schema_version: 1`, `taken_at_ms`, nullable `config_schema`/`database_schema` and nullable fixed `config_file`/`database_file` names. Null records actual absence; it never invents default config bytes. A `<name>.pending` directory becomes completed only after all files and the manifest are written and synced. Three recognised completed sets are retained across config-only and coordinated DB/config backups; unrecognised content is preserved. New manifests persist a positive checked `sequence`, allocated from the highest recognised committed sequence while holding the single-writer lease. Retention follows that creation order across restarts and backwards clock changes, and always excludes the set just committed from deletion. Existing version-one manifests without a sequence remain readable: they rank before sequenced sets, ordered by their recorded timestamp and path because their true creation order was not recorded. Timestamp directory collisions and sequence exhaustion fail closed before publishing or pruning any prior set. Failed callbacks never prune existing snapshots. A retention failure aborts migration and may leave extra complete sets; the current validated snapshot is retained. Timestamp overflow, a callback failure or a failed backup refuses migration and leaves the previous config unchanged. #81 adds the SQLite `backup_meta` row and integrity-checked database writer to this common namespace.

The application bootstrap now installs the coordinated SQLite callback for config migration when `data/tallyline.db` exists. It first validates supported config bytes and refuses a future database before replacing config. Schema-one SQLite requires this same coordinated callback before its schema-two forward transaction. When both files migrate, the config hook reuses only the exact matching previous schema and byte snapshot. Initial database absence continues to use the strict config-only branch before creating the first database. Failure of either backup component refuses startup processing.

Corrected 2026-11-02: the application database now uses schema 7 for price/status review decisions, manual attachment decisions, private crop digests and dated account screenshot requirements. Existing schemas 1–6 require the same verified coordinated backup before forward migration. Existing Report versions, observation times and decisions are preserved; legacy selections receive no invented private-copy digest. Configuration remains schema 4. Older schema-six binaries refuse database schema 7. Private source-scale crop files remain in the durable data directory across restart and original deletion; restoring database/config backups does not purge those files. Draft evidence is never purged automatically. Full release/queue restoration acceptance remains pending its lifecycle implementation.
