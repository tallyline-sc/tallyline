# Windows owned-process contract

> **Doc type:** Living reference — source primitive and harmless Windows contracts; runtime admission and product composition remain open. Last reviewed: 2026-11-07.

`adapter-platform::api::OwnedProcess` creates one supplied absolute executable suspended in a new unnamed job through create-time `JOB_LIST`, with an explicit `HANDLE_LIST` containing only its three child stdio ends. The public command supplies an explicitly deletable caller-owned private directory, cwd, cleared environment and finite capture bound. Its caller remains responsible for executable/native/profile admission and ownership of that directory. Canonical path preparation is not a replacement-safe executable certificate or a hostile-code sandbox.

The exact Windows x64 MSVC packet uses windows-sys 0.61.2/windows-link 0.2.1 and adds only Security, JobObjects, Pipes and IO on `x86_64-pc-windows-msvc`. There is no TCP helper feature or endpoint observer. The approved packet's first twenty Win32 functions are registered individually in 09 §3a. No dependency/native-source version, DLL redistribution, engine, model or inference is admitted by this primitive.

Before creation, job limits include kill-on-close, explicit committed-memory/process-count/below-normal-priority limits and a CPU hard cap, with breakaway flags absent. Read-back checks precede creation and every successful retained-root observation. The limits govern their Windows job metrics, not physical RAM, GPU memory, disk or network isolation. A live root's retained process handle, creation time, job membership, complete membership snapshot and priority must agree before its one permitted resume. The opaque adapter-local `OwnedProcessGeneration` is separate from Recognition's existing MetadataGeneration and supplies no metadata/private-input admission. Each lifetime creates one private shared allocation; the process, observations and explicitly cloned tokens retain it, and equality compares allocation identity. Shared ownership keeps that allocation distinct until all observations/tokens have gone, including after process cleanup, without a mutable global allocator. Tokens expose no integer or address and provide no ordering or persistence identity.

The bounded aligned startup allocation and boxed handle arrays stay stationary through attribute-list destruction. Parent copies of child pipe ends are explicitly closed after creation; returned process/thread, parent stdio and job handles are not inherited. Pipe reads have one synchronous owner, finite available-byte reads and per-stream retained-byte caps. Output overflow is retained as a typed failure while further bytes are discarded during finite cleanup. The adapter creates no runtime, thread or worker pool. Blocking calls belong on the app-owned bounded worker when later composed.

Cancellation revokes synchronously before cleanup. One positive budget, at most five seconds, covers owned-job termination, retained-root exit, complete current member/active-count agreement, stdout/stderr EOF, explicit handle closure and requested private-state deletion. Unknown process counts are None. Failures and missing observations produce Incomplete; closing the job as fallback is not release evidence. Startup preserves its primary failure and post-create reconciliation/cleanup results; resume preserves its underlying failure. The failed-startup cleanup deadline is established before retained-root reconciliation and passed unchanged to all subsequent cleanup work. Fallback drop reports incomplete cleanup without dumping captured output. Report Debug output includes release outcomes, counts, EOF/closure/deletion flags, output byte lengths and typed failure summaries. Startup/resume/cleanup diagnostics include only I/O error kinds and optional OS codes, never arbitrary nested error messages or captured output; explicitly requested output/error accessors retain their original data. Synchronous OS/file work cannot be pre-empted; post-operation deadline checks refuse a successful release claim after expiry.

## Public contracts and evidence limits

Corrected 2026-11-07: `crates/adapter-platform/tests/local_model_process.rs` runs through ordinary Cargo without a custom fixture-root environment prerequisite. Its exact same-test-executable children are launched by the public primitive. RAII temporary directories use the standard configured temporary location and remain owned until marker, private-state and descendant cleanup completes; local agent runners set `TEMP` and `TMP` under their task directory in `D:/Coding/Agents`. Execution markers live outside requested child-private state and are published only after exclusive writes, sync, close and output flushing. Contracts pair a sustained suspended interval and cancel-before-resume zero marker with actual resumed execution, fixed stdout/stderr and a live retained root. A nested executed fixture increases the parent's observed active membership and both roots disappear with complete job/EOF/handle cleanup. Windows can include additional associated helper processes; the test does not assume exactly two members.

Bounded-output overflow and private-directory replacement by a file retain typed incomplete cleanup after actual process release. The oversized-command public constructor had behavioural RED before the UTF-16 bound was added; the missing initial API and later member-count method had compiler RED. The first paired native run and additional overflow/deletion cases are supporting passing evidence, not separate behavioural RED claims. An initial descendant test's exact-two assumption failed on an observed count of four; correcting that fixture assumption is not a product fix.

Corrected 2026-11-07: the actual resumed fixture produced behavioural RED when numeric captured-output bytes appeared in report Debug, followed by GREEN for summary-only normal/pretty Debug. Public synthetic error construction similarly produced diagnostic privacy RED/GREEN. Retained-observation replacement lifetimes are supporting non-reuse regression evidence. The late failed-startup reconciliation deadline fix is established by source-flow review; no rare delayed native-call runtime RED or exhaustive timing acceptance is claimed.

These contracts establish the measured harmless Windows cases. They do not establish abrupt supervisor-death/last-job-close acceptance, every startup failure/cancellation interleaving, denied breakaway execution, physical weak-hardware fit, Linux ownership, actual engine/native/profile closure, network locality or installed-package acceptance. TCP ownership/session integration is the next dependent unit and must reuse Recognition's metadata identity through the permitted Workflows edge. No Workflows/App/controller wiring, startup launch or private input is added here. AI remains Off by default.

## Guard and legal-profile boundary

`supply-chain/owned-process-windows.json` records the actual complete Windows target Cargo feature union, exact four-feature declaration and complete permitted declaration baseline for every SDK declaration requesting any packet feature. The baseline binds owner name/version/source/workspace membership and dependency source/requirement/kind/rename/optional/defaults/target/features/registry, including existing older SDK declarations. Feature sets are order-independent. `xtask::owned_process_scope` checks declaration owner, target, source/version/defaults/features, resolved SDK version/complete union and windows-link identity before workspace build/test. Wrong targets, owners, extra features, alternate versions and declaration drift are refused even when a second declaration requests only Security, Pipes or IO while the valid Platform edge and resolved union remain intact. Inactive zbus/uds_windows declarations remain recorded without granting resolved activation; the existing native guard still rejects their forbidden reachable identities/features. The existing zbus/NSS/renamed-edge and Security_Authorization/IpHelper exclusions remain intact; this unit needs no exemption from them.

The selected source packages and legal component identities remain unchanged. Only the changed canonical manifest input hash is refreshed in the existing legal profile; no regenerated catalogue/notices or matching-host Linux run is implied. Windows SDK binding bytes remain governed by Cargo's exact source identity and the sealed source review. Hardware/native/whole-milestone completion is not claimed.
